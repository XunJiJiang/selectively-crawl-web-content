# SCWC 终端进一步设计方案

状态：用户已确认并进入实现。使用说明与实现入口见 [终端 README](../projects/terminal/README.md)。本文保留设计契约和验收要求，平台验证范围以使用说明为准。

## 1. 工程边界与启动链

新增 `projects/terminal`，以 TypeScript / ESM 开发，单独提供 package.json、tsconfig 和测试配置。核心保留 HTTP、插件宿主、缓存及业务命令；终端负责全屏界面、窗口管理、历史记录、确认、持久化及核心进程的启动与重启。

```text
setup.ts（源码入口：构建准备、解析启动参数）
  └─ terminal（长驻：唯一持有用户终端 stdin/stdout）
       └─ core（IPC 模式，stdout/stderr 被捕获）
            ├─ 插件宿主 A
            └─ 插件宿主 B
```

`setup.ts` 不再代理键盘输入，也不再拥有 restart 循环，只把参数交给终端启动器。重启只替换 core 及其插件宿主，终端自身、标签顺序、输出和命令历史保持存活。

直接运行 `projects/server/index.ts` 或核心可执行文件：使用原有 stdin 命令模式。终端启动核心时传 `--interaction=ipc`，核心不注册 stdin 监听；IPC 未连接时明确报错，不静默退回另一种模式。两种模式共享命令注册与执行逻辑。

首期通过本地父子进程 IPC 通信，不新开网络端口。未来若支持远程终端，再添加独立且有鉴权的传输适配器。

## 2. 渲染与输入实现

建议采用 Node.js `tty`、`readline.emitKeypressEvents` 及 VT/ANSI 控制序列，建立小型渲染层；屏幕进入 alternate screen、启用 raw mode 和 SGR mouse，退出时恢复光标、输入模式、鼠标模式和原屏幕。首期不增加终端 UI 框架依赖。

建议增加 `string-width` 与 `slice-ansi` 处理字符宽度、彩色截断：中文、emoji、组合字符和 ANSI 颜色码不能按 JS 字符串长度计算列数。鼠标、Unicode 宽度和屏幕刷新放在适配层，应用状态不依赖具体渲染库，必要时可替换渲染实现。

只在状态变化时刷新，合并一批日志再渲染；加载动画约 100ms 更新一帧，标题滚动约 300ms 移动一列。终端 resize 后重算布局并保留窗口的历史锚点。输出中的光标移动、清屏和 OSC 控制码会被过滤，SGR 颜色保留，防止插件输出破坏界面。

非 TTY 或 `TERM=dumb` 使用普通逐行输出与命令交互，停用鼠标和标签动画；不能依赖全屏 UI 的运行环境也可以正常启动、关闭核心。

## 3. 布局与窗口模型

```text
┌ 输出 0 │ cmd1 1 │ plugin ⠋ cmd2 2 │ …                  ┐
│                                                       │
│                  当前窗口的输出                       │
│                                                       │
├ 当前窗口有命令正在执行，是否确认关闭？ :y / :n          ┤
└ :s 2                                                  ┘
```

窗口状态至少包含：

```ts
interface TerminalWindow {
  id: string;                 // 创建时生成 UUID，持久化后恢复；关闭后不复用
  kind: 'output' | 'command';
  commandNumber?: number;      // cmdN 中的 N，最小未使用正整数
  defaultTitle: string;        // 输出 / cmdN
  task?: { executionId: string; mainCommand: string; status: 'running' | 'background' | 'cancelling' };
  output: OutputBuffer;
  scrollAnchor: ScrollAnchor;  // 历史行及换行偏移；末尾时跟随新输出
  history: string[];
  historyCursor: number;
  draft: string;
  historyDraft: string;        // 浏览历史前暂存的未提交输入
  selection?: { anchor: number; cursor: number };
}
```

默认创建固定输出窗口和 `cmd1`，输出窗口不能关闭。所有服务日志进入输出窗口；命令输出进入命令对应的窗口。窗口切换不会修改各自草稿、历史位置和输出滚动位置。

每个标签页（包括输出窗口）在创建时生成唯一且固定的 `windowId`，即上面的 `id`。切换、改标题、移动标签和重启核心不会改变这个 ID；恢复持久化窗口时沿用它。关闭后新建窗口必须生成新 ID，即使复用了相同 cmd 编号或标签序号，也不能接收旧窗口的输出。每次命令另生成唯一的 `executionId`，区分同一窗口内先后执行的命令。

编号分为两种：

- `cmdN` 的 N 是命令窗口的编号，关闭窗口后可复用最小空缺编号。
- 标签尾部数字是当前从左到右的序号，从输出窗口的 0 开始。`:s`、`:c` 和命令目标参数使用这个序号。收到命令时立即解析到稳定 `id`，之后的异步确认不再重新解释序号。

执行时标题替换为解析后的主命令，例如 `plugin ps` 显示 `plugin`，随后显示加载动画、cmd 编号与标签序号。函数尚未返回为 running；函数已返回但该次调用仍有插件主动报告的任务为 background，继续显示命令标题和加载动画。只有该次执行整体结束后才恢复默认标题，并把完成、失败或取消状态写入输出。进程级后台任务不关联某个命令窗口时，不占用该窗口的标题。

过长的标签：非活动标签显示省略号；活动标签或鼠标悬停标签滚动显示。可见宽度按字符列计算。标签总宽超出屏幕时显示对应方向箭头；点击箭头按一个标签移动，标签栏滚轮按字符列移动，浏览模式的左右键按一个标签移动。切换窗口后自动把目标标签移动到可见区。

输出按逻辑行存储，再按屏幕宽度折行，保留颜色。每窗最多保留 10,000 行或 10 MiB（先达到者为准），超出时记录一条历史截断提示。查看历史时新日志不会强制跳回末尾；滚动到末尾后恢复自动跟随。

## 4. 输入模式与快捷键

输入状态分为 `normal`（浏览）、`command`（普通命令输入）、`global`（全局命令输入）、`confirmation`（确认）。同一按键只由当前模式处理，confirmation 优先级最高。下面的普通操作在确认模式中都停用，确认规则单独说明。

| 输入 | 行为 |
| --- | --- |
| Tab / Shift+Tab | 切换下一 / 上一窗口；首次尝试越过边界时停留，再次连续输入同方向键时循环，具体规则见下文 |
| 点击标签 | 切换窗口 |
| 左 / 右 | normal 中滚动标签栏；command / global 中移动输入光标 |
| Shift+左 / Shift+右 | command / global 中选择输入文本；普通输入替换选区，Backspace / Delete 删除选区 |
| 上 / 下 | normal / global 中滚动当前窗口输出；command 中切换本窗命令历史 |
| 输出区滚轮 | 滚动当前窗口输出，与是否正在编辑输入无关 |
| `:` | 仅 normal 中进入全局命令模式；command / global 中作为普通字符 |
| Enter / `i` | 仅 normal 的命令窗口中进入 command；输出窗口保持浏览。command / global 中 Enter 提交当前输入，`i` 为普通字符 |
| Esc | command / global 中回到 normal，保留对应草稿；normal 中不退出程序；confirmation 中取消 |
| Ctrl+C | command / global 中仅清除对应草稿及选区，保持输入模式；normal 中有当前任务则请求取消，否则进入退出流程；confirmation 中仅取消确认 |

Tab 边界规则：已经位于最后一个窗口时，第一次 Tab 不切换并设置越界标记；600ms 内再次 Tab 才切换到第一个窗口。已经位于第一个窗口时，Shift+Tab 对称处理。超时、其他键、鼠标操作或窗口列表变化都会清除标记。普通移动到边界不算一次越界尝试；只有一个窗口时始终停留。这里的“连续两次”是应用收到的两个按键事件，不依赖传统终端无法可靠提供的按键松开事件。

切换窗口时保存原窗口的命令草稿与选区；command 模式切到另一个命令窗口时继续编辑目标窗口草稿，切到输出窗口时回到 normal。global 模式切换窗口后仍保留 global 模式与全局草稿；`:w` 等默认目标在按 Enter 提交时取当前窗口，`:run N` 等显式序号也在提交时解析为固定 ID。

普通命令草稿与全局命令草稿分别保存。global 草稿不包含用于显示的首个 `:`；Esc 后再次从 normal 按 `:` 时恢复这份草稿，不额外插入冒号。global 中继续输入冒号则插入字面字符，允许 `:run 1 fetch https://example.test` 等参数。普通命令接受执行或全局操作落实后清空对应草稿；进入确认/等待取消阶段时暂不清空，参数错误、拒绝执行、替换失败或取消确认时保留原草稿。确认输入使用独立缓冲，不覆盖草稿。

command 中第一次按上键前保存尚未提交的草稿；向下越过最新历史后恢复这份草稿。切换窗口后仍保留各窗历史游标。global 的上下键只滚动输出，不修改普通命令历史。

原要求“任意窗口输入 :”明确为任意窗口的 normal 模式中可按 `:` 进入 global；已经在 command / global 中时不切换模式，避免截获 URL、路径或命令参数中的冒号。

主要操作使用普通方向键、Tab、Enter、Esc 与全局命令；保留 Ctrl+C 作为可选便利键，取消和退出也可用 `:cancel` / `:q`。Shift+方向键、Shift+Tab 只有在终端发送可区分的编码时才能识别；无法识别 Shift+方向键时按普通方向键移动，不承诺文本选择。窗口选择可用 `:s N` 或鼠标完成。增强键盘协议放在输入适配层按支持情况启用，不把 Cmd/Ctrl 方向键列为默认快捷键。

确认模式暂停窗口切换、历史操作、滚动和插件命令：用户输入完整 `:y` 并按 Enter 才确认；`:n` 加 Enter、Esc、Ctrl+C 或其他无关按键取消。逐个接收 `:`、`y` 或 `n`、Enter 的合法中间输入不立即取消。其他全局命令不会执行；取消所消费的输入也不会重新送入普通模式。每个确认保存操作类型、固定 windowId、旧 executionId（如有）与待执行命令，不能因标签序号变化或任务结束而操作另一项任务。确认结束后清空确认缓冲，恢复之前的模式。确认提示可折成多行，减少输出区高度，极窄屏幕仍保留输入行。

## 5. 全局命令

| 命令 | 行为 |
| --- | --- |
| `:q` | 退出；有核心任务、命令或插件后台任务时按原文提示确认 |
| `:w` | 关闭当前命令窗口；函数仍在执行或该次调用仍有主动忙状态时按原文提示确认；输出窗口拒绝关闭 |
| `:r` / `:restart` | 重启核心；有任务时按原文提示确认 |
| `:s N` / `:switch N` | 切换到标签序号 N |
| `:c N` / `:close N` | 关闭标签序号 N；与 `:w` 相同的确认与保护 |
| `:new` | 创建并聚焦一个命令窗口，补齐原待办缺少的创建入口 |
| `:run N <命令>` | 空闲时直接在指定命令窗口执行；已有任务时提示“当前窗口有任务正在执行，是否终止并执行新命令？”，确认后先终止旧任务，结束后再执行新命令 |
| `:cancel [N]` | 取消当前或指定命令窗口的任务 |
| `:help` | 显示全局命令与快捷键 |

无效序号、参数错误、输出窗口上执行命令，均在底部显示错误。每个命令窗口同一时刻只允许一个执行上下文，包括函数返回后仍在进行的主动后台任务。普通 command 模式在窗口忙碌时拒绝提交，提示可通过 `:run` 替换或 `:new` 新建窗口。`:run` 是明确的替换操作，不是追加或同时运行。不同窗口可并行运行，但生命周期操作由核心串行处理。

`:run` 在确认前先检查新命令的基本语法和命令注册情况，再保存目标 windowId、旧 executionId 与新命令文本。`:y` 只取消那次旧执行；如果旧执行已结束就无需再取消，但目标已关闭或被另一执行占用时放弃本次替换并提示。只有收到旧执行整体结束，或确认其宿主已被强制停止，才允许新命令开始；取消失败则不启动新命令。强制停止插件宿主会使其命令失效；如果新命令依赖这个已停止的宿主，本次替换失败并提示先用 `:r` 重启核心，保留新命令草稿供重新提交，不自动重放。首期不额外引入单插件重新激活功能。

取消超时后的整宿主终止另按第 7 节确认影响范围，第一次“替换任务”的确认不能替代这次确认。等待取消期间窗口为 busy；新命令尚未开始就不写入该窗已执行历史。放弃或失败时保留全局草稿，用户可以修改后再次提交。

系统保留这些全局命令名。普通 `exit` / `restart` 也通过终端生命周期控制器进入同样的检查与确认流程，避免绕过确认；触发生命周期的控制命令本身不算需要确认的业务任务。新输出不影响待确认事项；关闭确认的目标任务在等待时已结束，仍按原 windowId 关闭原窗口；目标已不存在则提示并结束确认，不操作同序号的新窗口。

## 6. 终端与核心通信及输出归属

定义单独的共享 TypeScript 协议，所有消息携带 `version: 1` 和 `sessionId`，请求携带 `requestId`，执行相关消息携带 `executionId` 和 `windowId`；嵌套执行另携带 parentExecutionId。终端↔核心协议版本与现有核心↔插件宿主的版本分开维护，新增调用身份与任务消息时同步扩展插件 RPC 契约。

| 方向 | 消息 |
| --- | --- |
| 终端 → 核心 | `hello`、`command.execute`、`command.cancel`、`tasks.snapshot`、`lifecycle.exit`、`lifecycle.restart` |
| 核心 → 终端 | `ready`、`output`、`command.started`、`command.returned`、`command.finished`、`task.changed`、`snapshot`、`error`、`stopping` |

终端握手中提供固定 outputWindowId；执行请求提供目标 windowId 和新的 executionId。`ready` 包含最终 HTTP 端口、运行模式和可用命令目录。命令注册变化后推送目录更新。`command.returned` 仅表示命令函数返回或其返回的 Promise 已结束，附带该调用的主动任务状态快照；仍有主动忙状态时窗口继续忙碌。`command.finished` 表示该次执行整体结束，明确区分成功、失败、取消、宿主崩溃。核心重启后生成新 sessionId，终端丢弃旧会话的迟到消息；未知消息和协议版本不匹配给出可读错误。

### 6.1 为每次调用注入固定归属的 logger

目前插件宿主的 logger 只发送 `{ level, text }`，核心仅能知道它来自哪个插件。新方案需要在执行命令时创建一个新的 logger，把固定 windowId 及本次 executionId 封装在对象中：

```ts
type PluginLogger = SCWC.TLogger & {
  readonly pluginId: string;
  readonly windowId: string | null; // 终端模式使用固定 UUID，直接运行核心时为 null
  readonly executionId?: string;   // onLoad 等进程级日志可以没有执行 ID
  readonly sessionId?: string;
};
```

`info/pathInfo/warn/error` 保持原签名。对象及身份字段只读，日志方法闭包绑定这些字段，不能通过修改共享 logger 的 windowId 来切换归属。主命令和子命令都收到本次调用专用的 logger；两个窗口并发调用同一插件也有两个独立 logger。

插件 RPC 传递可序列化的身份数据，宿主在本地生成 logger 的方法；不把 logger 函数直接发送到 IPC。日志事件改为 `{ pluginId, windowId, executionId, sessionId, level, text }`，核心由对应插件连接确定 pluginId，并核对执行的归属，再转发给终端。

插件保存此次 logger、将它传给内部工具，或在函数返回后的异步回调中继续使用它，输出仍归属于原窗口、原执行，不受标签切换或下一条命令影响。`onLoad` 注入的 logger 固定归属于输出窗口；保存它不能代替命令调用的专用 logger，需要显示在命令窗口的代码应使用本次传入的 logger。

核心自身的命令日志也绑定同一个调用上下文。`AsyncLocalStorage` 用于核心命令帮助、共享工具和 console 捕获等没有显式 logger 参数的路径；显式注入的 logger 始终使用自己的固定归属。共享工具需要针对当前调用派生 logger，不修改任何已有 logger 的字段。

日志归属在创建调用时确定，与正在查看的窗口无关。原窗口已关闭时，迟到日志转入输出窗口并标注原 windowId、cmd 编号及 executionId；不投递给复用 cmd 编号的新窗口。原执行已结束但原窗口还存在时，迟到日志可继续显示在原窗口并保留旧 executionId，不使新执行的状态发生变化。

裸 `console.log` 或 stdout/stderr：插件宿主可包装 console / 输出捕获并关联调用上下文；无法可靠归属的非结构化输出统一进输出窗口，不猜测目标命令窗口。不改变日志在直接核心启动模式下的现有输出方式。

IPC 队列和输出缓冲设置上限，按批次发送。高频输出合并并在超限时插入丢弃统计，避免一个插件占满终端内存或阻塞其他窗口。核心意外退出时，所有受影响的执行标记为中断，保留输出；有限次数退避重启，反复启动失败后保持终端可操作并提示原因。

### 6.2 同时注入调用级 TaskReporter

核心在每次调用插件业务函数时同时提供 TaskReporter；不能只在 onLoad 中提供一个全局对象。命令保持前四个参数的位置，在末尾追加调用上下文，旧的四参数实现可以忽略新增参数：

```ts
interface PluginInvocationContext {
  readonly windowId: string | null;
  readonly executionId: string;
  readonly signal: AbortSignal;
  readonly tasks: TaskReporter;
}

// 主命令和子命令均使用相同约定。
execute(logger, options, unusedArgs, originArgs, context);
```

TaskReporter 的作用域绑定当前插件进程与 executionId，windowId 与本次 logger 相同；可在函数返回后由插件保留并解除主动任务。它与 AbortSignal 均在宿主内由 IPC 身份数据与取消消息创建，不直接序列化函数或信号对象。普通 API、控件、抓取等业务回调在各自现有 context 中扩展 tasks，不重排原参数；没有命令窗口的调用使用输出窗口归属。直接运行核心时也提供调用上下文，输出仍写普通控制台。

## 7. 任务状态接口与取消

### 7.1 两种主动报告作用域

在 `onLoad(logger, context)` 中注入进程级 `context.tasks`，供插件主动报告独立后台工作；按第 6 节，在每次业务函数调用中再注入调用级 TaskReporter。两者使用相同接口：

```ts
interface TaskReporter {
  begin(label?: string): { id: string; end(): void };
  setBusy(busy: boolean, label?: string): void;
}
```

`begin/end` 适合多个并发后台任务；每次 begin 创建独立任务 ID，end 幂等，建议在 finally 中调用。setBusy 是当前报告作用域的主动忙标记，两次 true 不累加，false 只撤销这个作用域的该标记，不结束 begin 产生的任务。

进程级 reporter 的作用域为当前插件宿主实例，直到宿主停止；调用级 reporter 的作用域为该次 executionId，函数返回时仍保留未结束的主动报告。不同调用的 setBusy 标记互不覆盖；进程级 false 不撤销某次调用的主动忙，调用级 false 也不撤销插件的独立后台任务。与命令窗口相关的后台工作必须使用本次调用注入的 reporter；如果使用保存的 onLoad reporter，则只算进程级忙状态，不占用某个窗口。

### 7.2 自动状态与主动状态合并

核心自动统计命令函数及其他业务回调是否已结束：调用前增加自动计数，同步返回后或返回的 Promise 完成/拒绝后在 finally 中减少。核心能判断返回的异步链是否完成，不能判断函数内部启动但没有返回或 await 的工作；这部分由插件主动报告。

每个调用作用域的状态分别存储，不使用一个会被自动结束覆盖的 busy 布尔值：

```ts
invocationBusy = automaticActiveCount > 0
  || manualBusy
  || activeReportedTasks.size > 0;

processBusy = processAutomaticActiveCount > 0
  || processManualBusy
  || processReportedTasks.size > 0
  || anyInvocationBusy;
```

这里“插件主动设置优先”的具体语义是：主动忙状态不会被函数返回、异常或自动计数归零清除。插件主动设为空闲只撤销自己的主动标记；函数仍未结束或有其他任务时，不能提前把整体显示为空闲。普通命令的完成判定必须等待该调用作用域所有忙来源都解除，不能仅依据 RPC 返回就发出 command.finished。

| 函数自动状态 | 插件主动状态 | 调用整体状态 |
| --- | --- | --- |
| 未返回 / 返回的 Promise 未结束 | 未主动设置或已 setBusy(false)，且没有 begin 任务 | busy / running |
| 已结束 | 未主动设置或已 setBusy(false)，且没有 begin 任务 | idle，发出 command.finished |
| 已结束 | setBusy(true) 尚未解除 | busy / background |
| 已结束 | setBusy(false)，但仍有未 end 的 begin 任务 | busy / background |
| 已结束 | 所有主动标记和 begin 任务已解除，但插件另有进程级任务 | 本窗口 idle；插件与整个程序仍 busy |

命令正常返回后若主动忙仍为 true，核心发出 command.returned 与状态快照，窗口继续显示原命令和动画，`:run` / `:w` / `:cancel` 仍视为有任务。插件后续通过同一个 reporter 解除最后一个主动状态时，再发出 command.finished。函数抛错但主动任务尚未解除时，先显示函数错误，继续保留忙状态，不能假定异常会终止独立后台任务。

主动报告更新在宿主本地同步生效，再通过 IPC 发送带作用域与递增 revision 的快照；函数返回消息携带同一份状态快照。核心忽略较旧 revision，避免把“函数已返回”的消息先当作空闲再处理主动忙状态。

每次新命令从全新的调用作用域开始。整体执行结束后 reporter 失效，迟到的 setBusy/begin 不能重新打开已完成执行或影响后续命令；重复 end/解除已结束的标记作为无影响操作。脱离返回 Promise 的后台工作必须在函数返回前 begin 或 setBusy(true)，不能等定时器实际触发后才登记。

示例：函数启动独立异步工作后立即返回，但窗口保持忙碌直到 finally 解除：

```ts
function execute(logger, options, unusedArgs, originArgs, context) {
  const tasks = context.tasks;
  tasks.setBusy(true, '后台处理');
  void doBackgroundWork(context.signal)
    .then(() => logger.info('后台处理完成'))
    .catch((error) => logger.error('后台处理失败', error))
    .finally(() => tasks.setBusy(false));
}
```

函数自动状态在同步返回后结束，但 tasks 的主动状态保留。同一个作用域内有多个并行后台工作时改用各自的 begin/end，避免第一个完成的工作用 setBusy(false) 过早撤销共用标记。

自动统计覆盖命令、抓取、API、控件、资源回调以及正在执行的 WebSocket 消息回调；退出/重启控制命令与生命周期卸载不是普通业务任务。常驻空闲 WebSocket 连接不算正在执行的任务。窗口忙状态只汇总该窗的执行作用域；退出/重启检查再聚合核心、业务插件和终端命令插件的全部作用域。

### 7.3 取消与退出

异步调用可通过 AbortSignal 协作取消，但当前插件函数和同步阻塞代码无法保证可取消。第一阶段在调用上下文提供 signal，RPC 新增取消消息。取消请求发给原 executionId，插件在清理后自行 end / setBusy(false)；核心不能因为发出了取消信号就抹掉主动忙状态，必须等函数结束且主动任务解除。RPC 超时也不能当作函数真实结束，宿主仍存活且未报告完成时保持未完成状态。

超时仍未结束时，提示“强制取消将停止整个插件进程，并中断该插件其他任务”；再次确认后按现有进程树清理方式终止宿主。只有确认宿主已停止，才清除该宿主全部自动与主动状态，将受影响执行标记为中断并让插件显示为停止。其他窗口、其他插件的任务不受状态清理影响。插件崩溃时同样清理该宿主的所有作用域；新宿主使用新的身份，旧 reporter 消息不生效。核心内建命令和终端插件不可取消的任务也必须走明确的超时/失败路径。

关闭忙碌窗口：确认后先取消该窗的执行及其主动后台任务，收到整体结束或完成强制终止后再删除窗口。`:run` 替换复用相同取消流程，结束后再检查新命令是否可执行。`:q` / `:r` 确认后停止接收新业务请求，取消/等待自动及主动任务，逐项卸载插件、保存状态，然后退出/重启。进程级后台任务的取消由插件的进程清理路径处理；插件报告一直未解除时仍进入明确的超时与强制流程。超时不能当作正常完成。

## 8. 持久化与恢复

新增 `SCWC_TERMINAL_STATE_FILE` 配置：默认源码模式在仓库根 `data/terminal/state.json`，生产终端在部署目录 `data/terminal/state.json`；相对路径以环境配置目录为基准。命令插件目录由 `SCWC_CMD_PLUGIN_DIR` 指定，源码默认 `projects/terminal/plugins`，打包后的建议默认部署目录 `terminal/plugins`。

状态采用版本化 JSON，保存固定窗口 ID、cmd 编号/顺序、活动窗口、输出缓冲、滚动锚点、各窗命令草稿、历史游标/暂存草稿、全局命令草稿、命令历史及执行状态。加载动画、光标闪烁、输入选区、确认提示和待确认的替换操作不保存；配置 token、Redis 密码不单独复制进状态。恢复后先进入 normal，用户按 i / Enter / `:` 再恢复编辑，避免启动时意外提交旧输入。

正常退出前停止任务并将中断原因追加到对应输出，再写状态。每 1 秒定时检查并保存脏快照，将该周期内变化合并为一次写入，避免持续输出导致纯防抖一直推迟保存；退出时立即完成最后一次保存。写临时文件再原子替换，保存前一个成功快照为备份。并发启动使用状态文件锁，第二个实例使用独立状态文件或报错，不互相覆盖。文件权限在支持的平台设为仅当前用户可读写。

下次启动遇到 running/background/cancelling 记录，均改为 interrupted 并追加“上次退出时被中断，未重新执行”。只恢复显示，不重放命令，也不恢复旧的主动 busy 标记、TaskReporter 或取消信号。坏文件先保留副本，再尝试备份，失败则恢复两个默认窗口并提示；不清空用户文件。输出窗口缺失时补回；重复 cmd 编号修复为最小空缺编号；缺失、无效或重复 windowId 为受影响窗口重新生成 UUID；活动窗口不存在时回到输出窗口。

SIGKILL 和断电无法运行退出钩子，所以只能保证恢复最近成功保存的快照，通常可能丢失最近约 1 秒输出；磁盘写入阻塞或保存失败时可能更久，不能保证严格上限。这个边界在文档和恢复提示中注明。

命令历史与日志可能包含用户输入的敏感内容。提供清除当前窗口历史/输出的命令和可关闭持久化的设置，明确状态文件路径，不作难以保证的自动脱敏承诺。

## 9. 终端插件契约

终端命令插件与核心业务插件使用不同目录和契约，不能互相当作入口加载。插件包含 package.json（main、enabled、apiVersion），入口导出 onLoad/onUnload，onLoad 中注册命令：

```ts
interface TerminalPluginContext {
  readonly tasks: TaskReporter; // onLoad 的进程级 reporter
  registerCommand(command: {
    name: string;
    description: string;
    execute(context: {
      args: string[];
      windowId: string;
      executionId: string;
      logger: PluginLogger;
      tasks: TaskReporter;     // 本次命令专用的 reporter
      signal: AbortSignal;
      write(text: string): void;
      invokeCore(command: string): Promise<void>;
    }): Promise<void> | void;
  }): void;
}
```

终端插件也由独立宿主进程加载，避免插件同步阻塞冻结界面，沿用现有有界 RPC 的机制。窗口操作、写入输出和调用核心由终端代理提供，插件不能直接使用用户终端的 stdin/stdout。首期以注册普通命令为扩展入口，不允许接管原始键盘或覆盖全局生命周期命令。

终端命令插件采用相同的固定 logger 归属与任务合并规则，write(text) 是本次 logger 的便利包装，不能依当前活动标签决定目标。invokeCore 创建带 parentExecutionId 的子执行，复用原 windowId，输出保留各自 executionId；子执行不占用第二个顶层命令槽，也不重复写入用户命令历史。调用适配器从发起请求到子执行整体结束持有父调用的任务句柄，之后结束句柄并使 invokeCore 的 Promise 完成，因此子命令的主动 busy 不会因外层函数返回而丢失。子执行也服从同一个取消流程。

命令重名时使用目录 ID 前缀并提示；系统命令保留最高优先级。插件加载、运行和卸载均有超时；插件失效只影响自己的命令。首期不支持热重载，插件变更重启终端后生效。普通插件仍拥有 Node 的文件/网络能力，进程隔离用于稳定性，不承诺安全沙箱。

## 10. 推荐实施顺序与验收

1. 通信协议和核心 IPC 模式：保持直接启动交互；验证同一插件在不同窗口并发时使用各自 logger，异步迟到日志仍归原窗口，关闭/复用编号不串窗，核心重启旧会话消息被丢弃。
2. 窗口状态与全屏渲染：默认双窗、创建/关闭、标题、滚动、输入模式、全局命令、确认、resize；验证 Tab 二次越界/超时、不同模式的冒号/上下键、普通/全局草稿恢复，以及中文宽度、大量标签、鼠标和非 TTY。
3. 任务状态与取消：注入进程级/调用级接口、自动统计、协作取消、强制终止影响提示；验证函数返回后主动忙保留、false 不清理其他作用域或未 end 的任务、并行 begin/end、返回消息与主动报告顺序，以及 `:run` 确认取消/旧任务已结束/强停宿主的分支。
4. 状态保存与恢复：原子写入、备份、持续日志下的定期快照、不重放任务；验证固定 ID 恢复、background 中断记录、退出、重启、SIGKILL、损坏状态和多实例。
5. 终端插件与入口切换：独立宿主、命令注册、环境目录配置；将 setup.ts 切换到终端启动器，补充使用文档。

核心设计测试采用 reducer 与协议集成测试；渲染和快捷键使用 PTY 自动化，再在 macOS / Linux / Windows 的常用终端人工验收。不能只依赖字符串快照证明鼠标或快捷键可用。

## 11. 本次建议确认的取舍

- 采用上述工程/IPC 边界与 Node 原生渲染适配层。
- 使用 `:new`、`:run`、`:cancel`；全局命令参数使用动态标签序号，内部绑定固定 UUID 与旧 executionId。`:run` 在确认并结束旧任务后启动新命令；强停宿主后依赖该宿主的新命令需先重启核心再提交。
- 冒号仅从 normal 进入 global，command / global 中按普通字符处理；普通与全局草稿分别保留；用 Enter / i 进入普通命令输入。
- 默认移除 Cmd/Ctrl 方向键，普通输入上下键切换历史；Tab / Shift+Tab 首次越界停留，600ms 内同向再次输入才循环。Ctrl+C 保留为可选便利键，主要流程都有全局命令入口。
- 为每次命令注入带固定 windowId / executionId 的独立 logger；同一插件并发和函数返回后的异步输出都保持归属。
- onLoad 提供进程级 context.tasks，每次业务调用另注入调用级 TaskReporter。函数返回仅结束自动状态，插件主动忙必须自行解除；函数仍在执行时，主动 false 也不能提前显示整体空闲。
- 插件不可协作取消时，强制取消会停止该插件整个宿主，必须明确确认影响范围。
- 正常退出完整保存，强杀恢复最近快照；执行中的命令只恢复输出，不继续执行。

本次已按确认的取舍实施终端工程、任务接口和 setup.ts 启动职责重构。新增 :clear、持久化开关及窗口/输出上限，用于管理历史数据与持续输出。
